# ExplainIT — Goal

## The goal
ExplainIT is a Visual Studio Code extension, published on the VS Code Marketplace (and Open VSX) for everyone, that does two things and does them completely.

First, it gives every code file a plain-English twin. When a code file is opened, a second file with the same name plus "_explain" (app.py gets app_explain.txt) opens beside it, listing every function in numbered order and describing each one in a few short, simple sentences that anyone can understand — one line saying what the function does, then two to five short lines saying how, with no jargon. The twin is a real text file that lives next to the code, but it is never committed or pushed to GitHub.

Second, it puts a human checkpoint in front of every change an AI coding assistant makes. When Claude Code, Codex, or Copilot tries to change code, the change is stopped before it reaches the disk, the file opens, and the person sees exactly what is changing — one function at a time — next to a fresh plain-English note explaining what changed and why it matters. Only when the person clicks Accept does that change land; then the twin is updated to match, and only then may the assistant continue to the next change. If the person rejects it, their reason goes straight back to the assistant so it can revise.

Everything runs on the person's own machine. The explanations are written by the AI assistants the person already has connected and pays for; ExplainIT ships no model, holds no keys, runs no server, sends no telemetry, and costs nothing extra.

## What it must do
1. On first use, ask the person's permission to use their connected assistant, detect which assistants are available (Copilot, Claude Code, Codex), connect to them with one click where needed, and guide anyone who has none connected yet.
2. Open the plain-English twin beside any code file the moment it opens, and let the person turn this automatic opening off if they prefer.
3. Write explanations in the fixed style shown in the reference screenshot: a number, the function name, one sentence saying what it does, then two to five very short simple sentences saying how. Explain only functions that are new or have changed; never re-explain code that has not changed, so the person's assistant credits are not wasted.
4. Work in every programming language the editor understands, with sensible fallbacks for languages the editor cannot outline itself.
5. Keep the twin honest as the code evolves: mark a section as outdated when its function changes, regenerate that one section on request, keep the twin scrolled in step with the code, and offer a "backfill the whole project" action that shows an estimate of the cost first, asks for confirmation, shows progress, and can be paused and resumed.
6. Keep twin files out of GitHub automatically, without touching the team's shared ignore file, and offer — never force — a shared ignore entry for teams that want one.
7. For Claude Code and Codex, physically stop every proposed file change before it touches the disk, show it per function with its plain-English meaning, and land it only on Accept. Accept must not be possible until the explanation is actually visible. Rejecting sends the person's reason back to the assistant. To avoid approval fatigue, the person can choose to accept the rest of a file or the rest of a session, and trivial changes such as whitespace or comment-only edits are grouped together.
8. Never let the assistants being checked switch the checkpoint off: writes to the checkpoint's own configuration, scripts, and records are refused outright, the checkpoint verifies its own integrity every session, and any instructions hidden inside code being explained are treated as data, never obeyed.
9. If ExplainIT itself ever stops responding, the assistant must fall back to its own normal permission prompt within a couple of minutes — never hang, and never slip through unchecked.
10. For Copilot, which offers no way for other extensions to stop its writes, add the per-function explanations to Copilot's own review of its changes, steer Copilot to work one function at a time, and say plainly in the interface that this path reviews changes rather than blocking them.
11. Record every proposed and accepted change in a tamper-evident local journal, save a restore point before every accepted change, and let the person restore any file with one click.
12. Provide a pause switch that turns the checkpoint off with a visible banner, a status indicator showing it is alive, a Doctor command that checks everything is installed, armed, and healthy (including a live test of the restore feature), clear messages for every empty, loading, and error state, and written guidance for the five most likely problems.
13. Measure the quality of its explanations with a built-in test and refuse any change to its prompts that makes them worse.
14. Behave like a product people rely on daily: fast (a cached twin opens in a blink, the first explanation streams within seconds), tested on Windows, macOS, and Linux, packaged and ready to publish, with an honest description of what it sends where — code goes only to the assistants the person already uses, under their existing agreements.
15. Work the same way for the Claude Code and Codex extensions inside VS Code as it does for their command-line tools: detect the extensions (and the assistant binaries they bundle) as connected assistants, use them to write explanations when no separate command-line tool is installed, and put the same per-function human checkpoint in front of every change they make from inside the editor — stopped before disk, explained per function, landed only on Accept, rejection reason sent back — with the Doctor confirming the checkpoint is armed for the extension path as well as the terminal path.

## How we know it is finished
The extension installs from its package into a fresh copy of VS Code and, without any manual setup beyond the person's existing assistant sign-ins, opens correct twins beside real code files, keeps them out of GitHub, and stops a real Claude Code or Codex edit for per-function approval exactly as described above — with every behavior in the list proven by automated tests that pass on all three operating systems. The same proof must hold when the edit comes from the Claude Code or Codex extension running inside VS Code, not only from the terminal tools. Publishing to the Marketplace and Open VSX is the one step that waits for Baharul's explicit go-ahead, because it is public and cannot be undone.
